## A. Completion summary

Built the **DashboardScreen** — the player's home screen and the
**FIRST real screen in CAGE EMPIRE** (every prior screen is a
placeholder). This task sets the pattern every subsequent Office
Mode screen will follow.

The Dashboard shows five sections, all compliant with
CONVENTIONS §14 (no raw attribute values) and §17 (UI reads
snapshots ONLY):

1. **Header** — H1 title + "Week N, Year N · Promotion Name" subtitle.
2. **Top Story + Other Headlines** (left column) — top_story headline
   as the marquee, the other 3 daily_headlines types as a bulleted
   list below.
3. **Promotion Status + Your Champions** (right column) — cash
   (formatted $X.XM), reputation + fan trust (voice-banded per §14),
   roster count, champion count, then a list of weight-class champions
   ordered heavyweight → strawweight.
4. **Fighter Watch** (3 cards) — Top Prospect (from fastest_rising
   headline), Hottest Streak (from fighter_descriptors momentum query,
   excluding the Top Prospect fighter for variety), Biggest Fall (from
   biggest_fall headline). Each card shows the fighter name + a voice
   phrase decoded from the "label||phrase" cache format.
5. **Recent News** (scrollable list) — last 20 news_items rows with
   topic badge + headline + date.
6. **Quick actions** — Schedule Event / View Roster / View Free
   Agents buttons (navigate via `state.set_active_screen()`).

Registered with GameState as `"dashboard"`; refresh callback is
`_refresh()`. The screen is preserved across navigations (pack_forget
on navigate-away, pack on navigate-to — same pattern as
SaveLoadScreen). `_refresh()` re-queries every data source and
re-renders every dynamic widget, destroying the old ones first.

## C. D-number decisions

### D1 — Source-of-truth map (§17 compliance)
The Dashboard's read map:
| Section | Source table | Why OK per §17 |
|---|---|---|
| Top Story + Other Headlines | `daily_headlines` | §17.3 cache table — interpretation layer is the only writer. |
| Fighter Watch (Top Prospect, Biggest Fall) | `daily_headlines` → `fighter_id` → `fighter_descriptors` (momentum + narrative_family voice phrases) | §17.3 cache tables. Fighter names from `fighters` (game state — names are NOT raw attribute values per §14). |
| Fighter Watch (Hottest Streak) | `fighter_descriptors` direct query (momentum='very_high'/'high') | §17.3 cache table. |
| Promotion Status (cash) | `promotions.current_cash` | Game-state money, not a fighter attribute. Per Task 6.3 brief + §14, OK to display formatted ($50.0M). |
| Promotion Status (reputation, fan trust) | `promotions.reputation`, `promotions.fan_trust` | Raw 0-100 game-state values — passed through local voice bands (D2) before display. NEVER shown as raw integers. |
| Promotion Status (roster count, champion count) | `fighters` COUNT, `titles` COUNT | Game-state counts, not fighter attributes. OK per §14. |
| Your Champions | `titles` JOIN `weight_classes` JOIN `fighters` (name only) | Game state — champion names + weight class names. NOT fighter attributes. |
| Recent News | `news_items` (headline, topic, published_at only) | Per Task 6.3 brief: "news_items is OK for display since it doesn't expose raw attribute values." Listed in §17.3 as a simulation table but the news feed is a fundamental game feature. Used ONLY for headline/topic/published_at — never for fighter attribute values. |

The Dashboard **NEVER reads from** `fighter_attributes`,
`fighter_personality`, `fighter_career`, `fighter_bios`,
`fighter_contracts` — those are the §17-forbidden simulation tables
that hold raw attribute values.

### D2 — Local reputation/fan_trust voice bands (transitional shim)
The interpretation layer hasn't fully populated
`promotion_descriptors` yet (the table exists per §17.3 but is empty
in the current world DB — verified during pre-flight). To honor §14
("no raw attribute values in the player-facing UI") WITHOUT waiting
for that population, the Dashboard applies its own voice bands to
the raw 0-100 `reputation` + `fan_trust` columns:

**Reputation bands:** 90-95 Legendary / 75-89 Highly Respected /
60-74 Well Respected / 40-59 Established / 25-39 Up-and-Coming /
10-24 Struggling.

**Fan trust bands:** 85+ Devoted / 70-84 Strong / 55-69 Loyal /
40-54 Wavering / 25-39 Restless / 10-24 Alienated.

The bands mirror §14.3's threshold approach (changes only on
band-boundary crossings, so the descriptor is stable across small
fluctuations). When a future interpretation task populates
`promotion_descriptors`, the Dashboard can switch to reading voice
phrases from there — the local bands will be removed at that time.
Verified: raw rep=85 → "Highly Respected" ✓, raw trust=75 →
"Strong" ✓ (matches the task spec's expected display).

### D3 — Hottest Streak card query
The other two Fighter Watch cards (Top Prospect / Biggest Fall) come
straight from `daily_headlines` rows (fastest_rising / biggest_fall).
The Hottest Streak card queries `fighter_descriptors` directly for
`momentum='very_high'` (or `'high'` as fallback), **EXCLUDING** the
fastest_rising fighter_id so the card shows a different face when
possible. Falls back to the first qualifying fighter if all
qualifying fighters are in the exclude set (better to show someone
than an empty card). Voice phrase decoded from the "label||phrase"
cache format. The momentum label filter uses the same
`SUBSTR + INSTR` trick the headline_engine uses (single source of
truth for the canonical-label filter).

Verified during smoke test: Top Prospect fid=80 (Timur Novikov,
momentum=very_high, narrative=prodigy → "the wunderkind everyone's
talking about"); Hottest Streak fid=22 (different fighter, since
fid=80 is excluded); Biggest Fall fid=14 (Daniel Gonzalez,
momentum=collapsing → "in freefall").

### D4 — Voice-phrase decoding (single source of truth)
The `fighter_descriptors` cache columns store `"canonical_label||
voice_phrase"` (per §17.4 + the interpretation engines' bulk-load
pattern). The Dashboard uses `interpretation.context_engine.
decode_phrase` to extract the player-facing voice phrase — the SAME
helper the interpretation engines use. No duplicate parsing logic.
This is the pattern every subsequent Office Mode screen should
follow when reading cache-table voice phrases.

### D5 — Layout structure
Mirrors the task spec's ASCII layout exactly:
- H1 title + subtitle (full-width).
- 2-column top row (Top Story | Promotion Status) — equal-weight
  grid columns with `uniform="top"`.
- 3-column fighter watch row (equal-weight grid columns with
  `uniform="watch"`).
- Recent News section (CTkScrollableFrame, fixed 200px height —
  scrolls within the visible area per the UI rules: max height with
  scroll overflow).
- Action button row (3 buttons, gold accent on the primary action
  "Schedule Event", neutral elevated surface on the secondary
  actions).

### D6 — Empty-state handling (graceful degradation)
Every section degrades gracefully when data is missing:
- No `daily_headlines` for top_story → "A quiet day across the
  promotions."
- No other headlines → "No other headlines today."
- No champions → "No champions yet — go win some belts."
- No fighter with very_high/high momentum → "No one's on a hot
  streak right now."
- No `news_items` → "The newswire is quiet."
Each section's query is wrapped in its own `try/except` so a single
failure (missing table, query error) doesn't abort the others. The
failure is logged to stdout; the section shows its empty-state.

### D7 — Action-button navigation
The three quick-action buttons call `state.set_active_screen()` to
navigate. They target screens that are not yet implemented
(`event_builder`, `roster`, `free_agents`) — those screens show the
placeholder label via `CageEmpireApp._navigate` until their own
tasks land. This is intentional: the Dashboard is the navigation
hub, even when destinations are placeholders. Each handler catches
`ValueError` (unregistered screen) and generic `Exception` so a
navigation failure logs a warning rather than crashing.

### D8 — Refresh pattern (mirrors SaveLoadScreen)
Dynamic widgets are tracked in instance lists:
`_headline_widgets`, `_champion_widgets`, `_promotion_status_widgets`,
`_watch_cards`, `_news_widgets`. `_refresh()` destroys them,
re-queries, re-renders. Static structure (titles, action buttons,
scrollable frames) is built once in `__init__`. Theme-change refresh
(`state.refresh_all()` after `set_theme()`) re-renders with the new
theme's colors/fonts because every widget construction calls
`get_theme()` at render time.

### D9 — Champion ordering
Champions are ordered by `weight_classes.display_order` ascending
(heavyweight first, strawberry last) — mirrors how fight sports
display title hierarchies (the biggest weight class is the marquee).
Falls back to `weight_class_id` ordering if `display_order` is NULL
via `COALESCE(wc.display_order, wc.weight_class_id)`. Verified:
Heavyweight, Middleweight, Welterweight, Lightweight, Strawweight —
in that order.

## F. Pattern this sets for subsequent Office Mode screens

Tasks 6.4-6.14 should follow this pattern:

1. **Class structure:** `XScreen(ctk.CTkFrame)` with a `_refresh()`
   method registered with GameState.
2. **Static structure in `__init__`:** `_build_*` methods create the
   section containers, titles, and scrollable frames. Dynamic
   widgets are NOT created here.
3. **Dynamic rendering in `_refresh()`:** destroys old dynamic
   widgets (tracked in instance lists), re-queries, re-renders.
4. **Theme:** every widget construction calls `get_theme()` at
   render time, so theme-change refresh picks up new colors/fonts
   automatically.
5. **§17 compliance:** read from cache tables for fighter
   interpretation data; read from game-state tables for non-fighter
   data. NEVER touch `fighter_attributes` /
   `fighter_personality` / `fighter_career`.
6. **§14 compliance:** no raw attribute values displayed. Use
   `decode_phrase()` on cache-table voice-phrase columns. Use local
   voice bands for any raw 0-100 game-state values (transitional
   shim until the interpretation layer populates the corresponding
   `*_descriptors` table).
7. **Empty-state handling:** every section degrades gracefully.
8. **Navigation:** use `state.set_active_screen(name)` for in-app
   navigation. Catch `ValueError` (unregistered screen) for forward
   compatibility with placeholder destinations.
9. **Registration in `app.py`:** import the screen, create an
   instance with `self.screen_container` as parent, register with
   GameState, extend `_navigate` to handle the new screen name
   (pack_forget on navigate-away to preserve state, pack on
   navigate-to).
