## What was built

Two thin interpretation modules that follow the EXACT pattern set by
the Context Engine (Task 2.2) and Career Phase Engine (Task 2.3):

1. **Narrative Families Engine** (`src/interpretation/narrative_
   families.py`) — 4 MVP story archetypes (Prodigy, Veteran, Fallen
   Champion, Cinderella Story). At most ONE family per active fighter
   (or NULL when no rule matches). Layers ABOVE career_phase —
   career_phase tells you WHERE the fighter is; narrative_family
   tells you the STORY being told about them right now.

2. **Legacy Engine** (`src/interpretation/legacy_engine.py`) — 4 MVP
   legacy states (Building, Established, Legendary, Forgotten).
   Applies to ALL fighters (active AND retired). The long-arc story
   of the fighter's career — DISTINCT from career_phase (the current
   snapshot). A retired HoF legend has career_phase=NULL but
   legacy_state="legendary".

Both engines follow the established Phase 2 pattern:
  1. Pure `compute_*` functions take primitive inputs, return canonical
     label strings (or None for narrative families). No DB, no RNG.
  2. Voice phrases are picked separately, RNG-seeded by fighter_id for
     determinism (no UI flickering between daily passes).
  3. Storage format is `"label||voice phrase"` per CONVENTIONS §17.4.
  4. Bulk-load pattern: one SELECT, Python loop, executemany UPDATE.
  5. Single-fighter refresh path for event-bus subscribers
     (<10ms budget).

## Architecture decisions (D-numbers)

### Narrative Families Engine

- **D1** — Reuse `encode` / `decode_label` / `decode_phrase` from
  `context_engine` (single source of truth for "label||phrase"
  format). Also reuse the momentum + career_phase canonical-label
  constants so we never typo a label string and silently break the
  rules.

- **D2** — 4 MVP families cut from the spec's 14 (per PHASE_2_PLAN
  §5, Task 2.4 + §4 MVP Cut). Excluded: gatekeeper, dynasty,
  dark_horse, late_bloomer, redemption_arc, final_run, changing_
  of_the_guard, giant_killer, nearly_man, champion_in_waiting.
  Canonical labels documented as enum-like constants to make Phase 3+
  extension safe.

- **D3** — At most ONE family per fighter (or NULL). The spec's
  "first match wins" rule — a fighter is classified as the FIRST
  matching rule in the priority order, not as a composite label.
  Keeps the UI label readable ("The Prodigy" is one story;
  "The Prodigy / Fallen Champion" is noise).

- **D4** — Priority order: Prodigy > Fallen Champion > Cinderella
  Story > Veteran (first match wins). The rules are mutually
  exclusive by career_phase (prodigy=prospect, fallen_champion=
  declining, cinderella=rising_contender, veteran=veteran) — so no
  fighter can match multiple families via the phase constraint alone.
  The priority order is a defensive safeguard for Phase 3+ when new
  families might overlap.

- **D5** — NULL is a valid outcome. Most fighters will NOT match any
  family — a 30yo rising_contender on a 2-fight win streak (momentum
  = stable) doesn't fit any of the 4 MVP archetypes. The UI shows
  their career_phase + momentum phrases but no family label. The
  bulk-load writes NULL for no-match fighters (clears any stale
  family from a prior daily pass — e.g., a prodigy who cooled off).

- **D6** — Skip inactive OR retired fighters. Same filter as
  `context_engine.compute_all_fighters` — narrative_family only
  makes sense for active fighters (career_phase + momentum are NULL
  for retired fighters; the legacy_engine handles the post-retirement
  story). The 60 HoF legends keep their NULL narrative_family.

- **D7** — RNG seeded by fighter_id (`Random(fighter_id * 31 + 17)`)
  so each fighter's voice phrase is DETERMINISTIC. Same seed formula
  as `context_engine` + `career_phase_engine` for consistency. The
  pure `compute_narrative_family` function NEVER touches RNG.

- **D8** — Bumped `snapshot_cache.ENGINE_VERSION` from "1.2.0" to
  "1.3.0" — the cache must rebuild on first run after this code lands
  (the narrative_family column starts NULL; the daily pass fills it).
  Combined with the Task 2.7 bump (D7 below), final ENGINE_VERSION
  is "1.4.0".

- **D9** — `compute_single_family` uses a targeted query (one SELECT
  on fighter_descriptors JOIN fighters JOIN fighter_career for this
  fighter_id only). MUST complete in <10ms per CONVENTIONS §17.5.
  Measured steady-state: 0.03ms (well under budget).

### Legacy Engine

- **D1** — Reuse `encode` / `decode_label` / `decode_phrase` from
  `context_engine` (same single-source-of-truth rationale as the
  narrative_families D1).

- **D2** — 4 MVP states cut from the spec's 6 (per PHASE_2_PLAN §5,
  Task 2.7 + §4 MVP Cut). Excluded: controversial, cult_hero.
  Canonical labels documented as enum-like constants for safe
  Phase 3+ extension.

- **D3** — Applies to ALL fighters (active AND retired). The spec's
  explicit requirement: legacy is the long-arc story, not the
  current snapshot. A retired fighter has career_phase=NULL but
  legacy_state="legendary" / "forgotten" / "established". The engine
  does NOT filter by is_active / is_retired — everyone gets a
  legacy_state. This is the KEY distinction from narrative_families
  (which only applies to active fighters).

- **D4** — Priority order: Legendary > Forgotten > Established >
  Building (first match wins). The order matters: a retired HoF
  legend who fought < 20 fights (rare but possible — a dominant
  champ who retired early) is "legendary" (HoF supersedes the "few
  fights" signal). A retired non-HoF fighter with < 20 fights is
  "forgotten" (supersedes "building" — they had their chance and
  didn't make a mark).

- **D5** — Defensive default: "building" for fighters who don't
  match any of the 4 explicit rules. The Building criteria as
  written has a gap: a fighter with 25+ fights and < 15 wins (a
  journeyman) doesn't match Building (total_fights < 25 fails) NOR
  Established (wins >= 15 fails). They default to "building" because
  the journeyman story is closer to "still building" than to
  "established" — they haven't done enough to be Established yet.
  This guarantees EVERY fighter gets a non-NULL legacy_state (per D3).

- **D6** — RNG seeded by fighter_id (same formula as the other
  engines — `Random(fighter_id * 31 + 17)`). Determinism verified
  by test case J.3 + J.4 (bulk + single refresh produce byte-
  identical values).

- **D7** — Bumped `snapshot_cache.ENGINE_VERSION` from "1.3.0" to
  "1.4.0" — the cache must rebuild on first run after this code
  lands (the legacy_state column starts NULL; the daily pass fills
  it).

- **D8** — `compute_single_legacy` uses a targeted query (one SELECT
  on fighters + fighter_career + LEFT JOIN hall_of_fame for this
  fighter_id only). MUST complete in <10ms per CONVENTIONS §17.5.
  Measured steady-state: 0.02ms (well under budget).

- **D9** — The HoF check uses a LEFT JOIN to hall_of_fame in the
  bulk SELECT (not a separate subquery). hall_of_fame has a PK on
  fighter_id so the LEFT JOIN doesn't fan out — one row in, one row
  out. This keeps the bulk-load pattern at ONE query total.

### Narrative families (4450 active fighters — 514 matched, 3936 NULL per D5)

| Family | Count | % of matched |
|---|---|---|
| veteran | 425 | 82.7% |
| prodigy | 57 | 11.1% |
| cinderella_story | 31 | 6.0% |
| fallen_champion | 1 | 0.2% |
| **(no match — NULL)** | **3936** | — |

The distribution looks realistic:
- Most matched fighters are veterans on flat/falling momentum — the
  "grizzled veteran refuses to fade" is the most common narrative
  among older fighters.
- A small minority of prodigies (young prospects on hot streaks) —
  rare because both conditions (prospect phase + high momentum) must
  hold simultaneously.
- Cinderella stories (28yo+ rising contenders on 5-fight win streaks)
  are rarer still — late bloomers on a tear are uncommon.
- Fallen champions are the rarest (1 fighter) — requires declining
  phase + held a title + falling/collapsing momentum. Most ex-champs
  are either retired (and thus skipped per D6) or not yet declining.
- 3936 fighters (88.4%) have NULL family — they don't fit any of the
  4 MVP archetypes. This is the expected MVP behavior; the full
  spec's 14 families would cover more.

### Legacy states (4510 total fighters — 100% populated per D3)

| State | Count | % |
|---|---|---|
| building | 3963 | 87.9% |
| established | 472 | 10.5% |
| legendary | 75 | 1.7% |
| forgotten | 0 | 0.0% |

The distribution:
- Most fighters are still building their legacy (early-to-mid career,
  not yet 25+ fights with 15+ wins). Realistic — the world seed
  skews toward younger rosters.
- 472 established fighters have a body of work (25+ fights, 15+
  wins, not in HoF). The respected veterans.
- 75 legendary fighters: 60 are the HoF inductees (retired legends),
  15 are active fighters on a legendary trajectory (2+ title reigns
  AND 30+ total fights).
- 0 forgotten: all 60 retired fighters are in the HoF (they're the
  "60 HoF legends"). The world seed doesn't have any retired non-HoF
  fighters with < 20 fights — Forgotten would trigger for those.
  This is correct engine behavior; the world DB just doesn't have
  any qualifying fighters.

  ("a prodigy turning heads early", "an all-time great"), not stats.
  Verified by test case L.
- §14 (Voice Layer): voice phrases contain no digits. Verified by
  test cases C + F + H.8 + L.4.
- §15 (Event Bus): unchanged — neither engine subscribes directly.
  Both are called by `snapshot_cache.refresh_fighter`, which IS
  subscribed (via `interpretation/__init__.py:register_subscribers`)
  to FIGHT_RESOLVED, FIGHTER_RETIRED, TITLE_CHANGED, CONTRACT_EXPIRED.
- §17.1 (UI Snapshot Rule): only writes to `fighter_descriptors`
  (a cache table). No simulation tables touched.
- §17.4 (Rich Not Thin): each column stores BOTH canonical label
  AND voice phrase, separated by `||`. Verified by test cases H +
  L.1. (NULL is allowed for narrative_family per D5 — most fighters
  don't match a family. legacy_state is always non-NULL per D3+D5.)
- §17.5 (Performance): bulk-load pattern (one SELECT + Python loop
  + executemany UPDATE). 102ms for 4450 active fighters
  (narrative_families), 73ms for 4510 total fighters (legacy).
  Both well under the <1s budget. Single-fighter refreshes: 0.03ms
  + 0.02ms — well under the <10ms budget.
