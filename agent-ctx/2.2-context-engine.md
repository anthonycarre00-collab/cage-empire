## What was built

The Context Engine — the first real interpretation-logic module in
Phase 2. It computes three derived labels (momentum, pressure,
trajectory) for every active fighter and writes momentum + pressure
to `fighter_descriptors` (the cache table established in Task 2.0c).

This task sets the PATTERN that all subsequent engines (career_phase,
narrative_families, legacy, etc.) will follow:
  1. Pure `compute_*` functions take primitive inputs, return canonical
     label strings. No DB, no RNG.
  2. Voice phrases are picked separately, RNG-seeded by fighter_id for
     determinism (no UI flickering between daily passes).
  3. Storage format is `"label||voice phrase"` per CONVENTIONS §17.4.
  4. Bulk-load pattern: one SELECT, Python loop, executemany UPDATE.
  5. Single-fighter refresh path for event-bus subscribers
     (<10ms budget).

## Architecture decisions (D-numbers)

- **D1** — Rank computation. The task spec suggested a heuristic
  (`rating > 1050 → estimated_rank = 15`). I rejected this — it
  produces wrong pressure readings (a fighter rated 1100 in a
  shallow division is rank 1, not 15). Instead I built a proper
  rank map: `_build_rank_map(conn)` does ONE SELECT on rankings,
  groups by (promotion_id, weight_class_id), sorts by rating DESC
  in Python, assigns rank 1..N per group. The bulk-load pattern is
  preserved (only 2 queries total — main fighter JOIN + rank-map
  SELECT).

- **D2** — Storage format. Per §17.4, each cache column stores
  `"label||voice phrase"`. Helper functions `encode/decode_label/
  decode_phrase` make this round-trip safe. Phrases containing `||`
  only split on the FIRST separator (defensive — though no current
  phrase uses `||`).

- **D3** — Determinism. RNG is seeded with `Random(fighter_id * 31
  + 17)` per fighter. The same fighter ALWAYS gets the same voice
  phrase across daily passes — no UI flickering. Verified by test
  case H.1 + H.2 (bulk compute + single refresh produce byte-
  identical values).

- **D4** — Skip inactive/retired. The SELECT filters
  `is_active=1 AND is_retired=0`. The 60 HoF legends / inactive
  fighters keep their NULL momentum/pressure. The UI doesn't list
  them on the active roster anyway.

- **D5** — Active contracts only. The JOIN to contracts filters
  `c.status='active'`. An expired contract shouldn't inflate
  pressure — the fighter is a free agent now (captured by the
  `is_free_agent` factor #7).

- **D6** — No trajectory column. The v3.10.0 schema only added
  momentum + pressure columns. Trajectory is a derived label that
  other engines (narrative_families, legacy_engine) compute on-
  demand from momentum + age via the pure `compute_trajectory`
  function exposed here. We don't store it.

- **D7** — Targeted single-fighter refresh uses subqueries, not
  `_build_rank_map` / `_build_champion_set`. Those helpers load
  ALL rows (good for the bulk pass, wasteful for a single fighter).
  The single-fighter path uses `SELECT COUNT(*) FROM rankings
  WHERE promo=? AND wc=? AND rating > ?` (rank = ahead+1) and
  `SELECT EXISTS(SELECT 1 FROM titles WHERE champ=? AND is_vacant=0)`.
  Steady-state: 0.41ms (well under the <10ms budget).

- **D8** — Defensive age. Missing/unparseable DOB defaults to age
  28 (prime). Keeps the daily pass from crashing on bad data;
  descriptor ends up "stable" (safe fallback).

- **D9** — Unranked = no pressure. If a fighter has no rankings
  row, `rank=None` → factor #4 not added. Matches real-world
  semantics (an unranked fighter has no expectations).

- **D10** — No schema migration. The task spec was clear: "no
  schema change in this task." The 6 new columns already exist
  (added in v3.10.0 Task 2.0c). `CODE_SCHEMA_VERSION` stays at
  3.11.0.

  `legacy_state`.

The `compute_trajectory_for_fighter(conn, fighter_id)` helper
exposed here lets future engines derive trajectory on-demand
without reimplementing the logic.

## CONVENTIONS compliance

- §13 (Design Law): momentum + pressure tell a STORY ("riding a
  hot streak", "fighting for their career"), not a stat. Verified
  by test case J.
- §14 (Voice Layer): voice phrases contain no digits. Verified by
  test cases D + F.6 + J.4.
- §15 (Event Bus): unchanged — context_engine doesn't subscribe
  directly. It's called by `snapshot_cache.refresh_fighter`, which
  IS subscribed (via `interpretation/__init__.py:register_
  subscribers`) to FIGHT_RESOLVED, FIGHTER_RETIRED, TITLE_CHANGED,
  CONTRACT_EXPIRED.
- §17.1 (UI Snapshot Rule): only writes to `fighter_descriptors`
  (a cache table). No simulation tables touched.
- §17.4 (Rich Not Thin): each column stores BOTH canonical label
  AND voice phrase, separated by `||`. Verified by test cases E + J.
- §17.5 (Performance): bulk-load pattern (one SELECT + Python loop
  + executemany UPDATE). 165ms for 4450 fighters, 0.41ms for
  single-fighter refresh — both well under budget.
