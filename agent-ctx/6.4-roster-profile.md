## A. Completion summary

Built the **two highest-traffic screens** in CAGE EMPIRE per
GUI_PLAN §5.7: the **Roster** (highest-traffic) and the **Fighter
Profile** (the most narrative-dense screen, where the interpretation
layer shines brightest). Together they account for the majority of
the player's screen time.

Both screens are compliant with CONVENTIONS §14 (no raw attribute
values) and §17 (UI Snapshot Rule — read from cache tables only):

### Roster screen (`src/ui/screens/roster.py`)

Shows every active fighter on the player's promotion as a sortable,
filterable, paginated table — every column except Name, Weight
Class, and Record shows an interpretation-layer voice phrase, NOT
the raw canonical label, NOT the underlying numbers.

Columns (all from cache + game-state, NEVER from
`fighter_attributes` / `fighter_personality`):
1. **Name + nickname** — `fighters.first_name` / `last_name` /
   `nickname` (game state, names per §14 OK)
2. **Weight Class** — `weight_classes.name` (game state)
3. **Career Phase** — decoded voice phrase from
   `fighter_descriptors.career_phase` (cache — §17.3)
4. **Momentum** — decoded voice phrase from
   `fighter_descriptors.momentum` (cache)
5. **Record** — `fighter_career.record_wins`/`losses`/`draws`
   formatted as "W-L-D" (career stats, OK per §14)
6. **Narrative** — decoded voice phrase from
   `fighter_descriptors.narrative_family` (cache — "(none)" if NULL)

Features:
- **Filter by weight class** (dropdown — populated from the player's
  roster)
- **Search by name** (case-insensitive substring on first_name +
  last_name + nickname)
- **Pagination** — 20 rows per page (per the brief's "show 20 at a
  time"), Prev/Next buttons + "Page N of M" indicator
- **Sortable columns** — click any heading to sort ascending; click
  again to toggle descending. Sort applied to decoded phrases (not
  raw "label||phrase" strings — D8)
- **Double-click a row** → `set_fighter_id(fighter_id)` on the
  Fighter Profile screen → `state.set_active_screen("fighter_profile")`
- **ttk.Treeview** (via `tkinter.ttk`, not ttkbootstrap — see D2)
  themed to match the Office dark palette via `ttk.Style().configure
  ("Roster.Treeview", ...)` using `ui.theme` colors

Registered with GameState as `"roster"`; refresh callback is
`_refresh()`. The screen is preserved across navigations (pack_forget
on navigate-away, pack on navigate-to — same pattern as
DashboardScreen). `_refresh()` re-queries the roster (filtered +
searched + paginated) + re-renders the Treeview.

### Fighter Profile screen (`src/ui/screens/fighter_profile.py`)

Shows a single fighter's full interpretation. This is where the
"Rich Not Thin" principle (§17.4) is most visible — every section
is a voice phrase, never a raw number.

Sections:
1. **Back button** — "← Back to Roster" navigates via
   `state.set_active_screen("roster")`.
2. **Header** — H1 name + nickname + "WC · Promo · Gym" subtitle.
3. **IDENTITY block** — 6 voice phrases in a 2-column grid:
   - CAREER PHASE (decoded from `fighter_descriptors.career_phase`)
   - MOMENTUM (decoded from `fighter_descriptors.momentum`)
   - PRESSURE (decoded from `fighter_descriptors.pressure`)
   - NARRATIVE (decoded from `fighter_descriptors.narrative_family`
     — "(none)" if NULL)
   - LEGACY (decoded from `fighter_descriptors.legacy_state`)
   - TRAJECTORY (derived on-demand via
     `compute_trajectory_for_fighter` — D3)
4. **BIO** — `fighter_bios.bio_text` (the supervisor's original prose)
5. **CAREER** — record (W-L-D), win_streak, loss_streak,
   title_reigns (career stats — §14 OK). Plus a gold "★ CHAMPION"
   badge if the fighter currently holds a title (D9).
6. **RECENT FIGHTS** — last 5 `fight_history` rows. Each row:
   `[W/L/D badge] vs Opponent Name (result_type, R{round}) · date`.
   Badge colored gold/crimson/steel.
7. **ATTRIBUTE PROFILE** — all 26 attributes as voice descriptors
   from `fighter_descriptors.attribute_descriptors` JSON, in a
   2-column grid. Logically grouped (striking → clinch/wrestling →
   grappling → durability → physical → mental — D7).
8. **PERSONALITY** — all 20 traits as voice descriptors from
   `fighter_descriptors.personality_descriptors` JSON, in a
   2-column grid. Grouped (combat behavior → mental toughness →
   social → career).

The Fighter Profile screen exposes a `set_fighter_id(fighter_id)`
method that the Roster calls BEFORE calling
`state.set_active_screen("fighter_profile")`. The method stores the
fighter_id + triggers an immediate `_refresh()` so the screen is
fully rendered by the time `_navigate` packs it (D2).

Registered with GameState as `"fighter_profile"`; refresh callback
is `_refresh()`. The screen is preserved across navigations.

### D2 — ttk.Treeview (via tkinter.ttk, not ttkbootstrap)

The brief says "use ttk.Treeview (via ttkbootstrap)". `ttkbootstrap`
is in `requirements.txt` but **not installed** in this environment
(verified during pre-flight — `import ttkbootstrap` → `ModuleNotFoundError`).
The standard `tkinter.ttk.Treeview` is functionally identical — the
only difference is ttkbootstrap auto-themes it.

We achieve the same dark theme manually via:
```python
style = ttk.Style()
style.theme_use("clam")  # clam is the most themeable on Linux
style.configure(
    "Roster.Treeview",
    background=theme.colors.bg_surface,  # #1a1d23
    foreground=theme.colors.text_primary,  # #e8eaed
    fieldbackground=theme.colors.bg_surface,
    bordercolor=theme.colors.bg_border,
    rowheight=28,  # touch-friendly per UI rules
    font=("Inter", 12),
)
style.map(
    "Roster.Treeview",
    background=[("selected", theme.colors.bg_surface_elevated)],
)
style.configure(
    "Roster.Treeview.Heading",
    background=theme.colors.bg_surface_elevated,
    foreground=theme.colors.gold,  # #d4a55a
    relief="flat",
    font=("Inter", 13, "bold"),
)
```

This keeps the Roster visually consistent with the rest of the CTk
shell without adding a runtime dependency that isn't yet installed.
When `ttkbootstrap` lands, the only change needed is to swap the
Style setup — the Treeview widget itself is unchanged.

The style is rebuilt on every `_refresh()` so theme-change refresh
picks up the new colors (mirrors how DashboardScreen rebuilds every
widget on `_refresh`). The style NAME is constant
(`"Roster.Treeview"`) so the Treeview widget itself doesn't need to
be recreated.

### D3 — Trajectory derivation

Per `context_engine.D6`, trajectory isn't stored as a cache column —
it's derived on-demand from `momentum` + `age`. The Fighter Profile
calls `compute_trajectory_for_fighter(conn, fighter_id)` which
reads `fighter_descriptors.momentum` (cache) + `fighters.date_of_birth`
(game state), applies `compute_trajectory`, and returns the
canonical label. The label is then passed to `get_trajectory_phrase`
to get the voice phrase. Both helpers live in
`interpretation.context_engine` — single source of truth.

This is §17-compliant: the only DB reads are from the cache
(fighter_descriptors) + game-state (fighters.date_of_birth — a date,
not an attribute).

Verified during smoke test:
- Fighter 1 (Hiroki Nakamura, momentum=falling, age 18) → trajectory
  = "declining" → "past their best days" (slightly awkward for an
  18-year-old but the algorithm says declining — known voice.py
  limitation, out of scope for Task 6.4).
- Fighter 578 (Anthony Evans, momentum=stable, champion) →
  trajectory = "stable" → "neither rising nor falling".

### D4 — `set_fighter_id` + late refresh

The Roster calls `set_fighter_id(fighter_id)` BEFORE navigating.
The method:
1. Stores the fighter_id on `self._fighter_id` (with try/except
   int conversion — defensive against bad input).
2. Calls `_refresh()` IMMEDIATELY — so the screen is fully rendered
   by the time `_navigate` packs it.

`set_active_screen("fighter_profile")` then triggers
`state.refresh("fighter_profile")`, which calls `_refresh()` AGAIN
— harmless (idempotent — `_refresh` destroys old dynamic widgets
before re-rendering).

The double-refresh is intentional: `set_fighter_id`'s immediate
refresh ensures the screen is ready even if `state.refresh` somehow
doesn't fire (e.g., if the screen was already active, which
shouldn't happen but defensive).

### D5 — Defensive against missing data

Every section degrades gracefully when data is missing:

**Roster:**
- No fighters in roster at all → "Your roster is empty. Sign some
  free agents to build your stable."
- Filter excludes everyone → "No fighters match this weight class."
- Search excludes everyone → "No fighters match '<term>'. Try a
  different name."
- No `fighter_descriptors` row for a fighter → the career phase /
  momentum / narrative columns show "(uncached)" rather than
  crashing.

**Fighter Profile:**
- No `fighter_id` set → "No fighter selected. Return to the Roster
  and pick a fighter."
- `fighter_id` not in DB → "Fighter not found."
- No `fighter_descriptors` row → identity block shows "(uncached)"
  for each phrase; attribute/personality sections show "Attribute
  descriptors not yet computed." / "Personality descriptors not yet
  computed."
- No `fighter_bios` row → bio section shows "No bio available for
  this fighter."
- No `fighter_career` row → career section shows "0-0-0" record +
  "0" for streaks/reigns (the `_format_record` helper handles None
  components).
- No `fight_history` rows → recent fights section shows "No fights
  on record yet."
- No `titles` (not a champion) → career section omits the "★
  CHAMPION" badge.
- Malformed `attribute_descriptors` / `personality_descriptors`
  JSON → caught by `json.JSONDecodeError` try/except; section shows
  the "not yet computed" message.

Each section's query is wrapped in its own `try/except` so a single
failure (missing table, query error) doesn't abort the others. The
failure is logged to stdout; the section shows its empty-state.

### D6 — Identity block layout

The 6 voice phrases (CAREER PHASE / MOMENTUM / PRESSURE / NARRATIVE
/ LEGACY / TRAJECTORY) are rendered as a 2-column grid (label |
phrase) inside a card. Labels are gold (matches Dashboard's H2 panel
titles); phrases are `text_primary` (high contrast). Each row is a
CTkFrame containing two CTkLabels (label left, phrase right) — the
phrase wraps to 600px so long phrases like "an up-and-comer

### D7 — Attribute + personality grid layout

The 26 attributes are rendered as a 2-column grid (label | descriptor)
— same pattern as the identity block. 26 attributes / 2 columns =
13 rows. Each cell contains:
- Label (humanized attribute name, gold caption font)
- Descriptor (voice phrase, body font, wraps to 300px)

The 20 personality traits are similarly a 2-column grid = 10 rows.

Both grids are inside their own card with a gold H2 section title
("ATTRIBUTE PROFILE" / "PERSONALITY"). The attribute order is
grouped logically so the player can scan by category (D7 — see
`_ATTRIBUTE_DISPLAY_ORDER` + `_PERSONALITY_DISPLAY_ORDER`):

**Attribute groups (26 total):**
- Striking (7): punch_power, punch_accuracy, kick_power, kick_accuracy,
  head_movement, footwork, clinch_striking
- Clinch & Wrestling (8): clinch_offense, clinch_defense,
  cage_wrestling, takedown_offense, takedown_defense, top_control,
  bottom_game, scramble_ability
- Grappling (2): submission_offense, submission_defense
- Durability (4): chin, durability, recovery_rate, cardio
- Physical (3): strength, speed_explosiveness, flexibility
- Mental (2): fight_iq, adaptability

**Personality groups (20 total):**
- Combat behavior (5): aggression, composure, risk_taking,

- Mental toughness (5): focus, discipline, grit, resilience,

- Career (6): ambition, loyalty, coachability, professionalism,

Any attribute/trait in the JSON not in the display-order list is
appended at the end (defensive against schema drift — D5).

### D8 — Sortable columns

Treeview heading clicks sort the underlying data by that column.
The sort state is tracked in `self._sort_column` + `self._sort_reverse`.
Default sort is by `fighter_id` ascending (insertion order — mirrors
the seed order, which is roughly chronological by debut). Clicking
a heading toggles asc/desc.

The sort is applied in Python (not SQL) because the voice phrases
need `decode_phrase()` before sorting — sorting raw "label||phrase"
strings would sort by the canonical label, not the player-facing
phrase, which is unintuitive (the player wants "riding a hot streak"
sorted alphabetically with other "R" phrases, not with "high" /
"very_high" / "stable" / etc. labels). Sorting in Python after
decode is fine for ~1000 rows (verified <30ms during smoke test).

Special case: the Record column sorts by total fights (wins +
losses + draws), not by string comparison — so "10-20-2" sorts as
32 fights, not as the string "10-20-2" (which would sort
lexicographically wrong).

### D9 — Champion badge

If the fighter is currently a champion
(`titles.current_champion_fighter_id = fighter_id` AND
`is_vacant = 0`), a gold "★ CHAMPION — {WC name} ({Promo name})"
badge is rendered at the top of the career section. This is
game-state data (titles table), NOT a fighter attribute — OK per §14.
The badge is a visual flourish that makes the profile feel alive
when the player is looking at a champion.

Verified during smoke test: Anthony Evans (fid=578, Welterweight
champion in Alpha Combat Federation) → "★ CHAMPION — Welterweight
(Alpha Combat Federation)" rendered in gold.

### D10 — Refresh pattern (mirrors DashboardScreen)

Dynamic widgets are tracked in instance lists
(`_header_widgets`, `_identity_widgets`, `_bio_widgets`,
`_career_widgets`, `_fights_widgets`, `_attr_widgets`,
`_pers_widgets` for the Fighter Profile; the Treeview clears itself
via `tv.delete(*tv.get_children())` for the Roster). `_refresh()`
destroys them, re-queries, re-renders. Static structure (H1 title,
section titles, scrollable frames, Treeview widget, filter row,
pagination bar) is built once in `__init__`. Theme-change refresh
(`state.refresh_all()` after `set_theme()`) re-renders with the new
theme's colors/fonts because every widget construction calls
`get_theme()` at render time. The Roster's `_apply_treeview_style`
is re-applied on every `_refresh` for the same reason.

## F. Pattern this sets for subsequent Office Mode screens

Tasks 6.5-6.14 should follow this pattern (extending the pattern
Task 6.3 set):

1. **Class structure:** `XScreen(ctk.CTkFrame)` with a `_refresh()`
   method registered with GameState.
2. **Static structure in `__init__`:** `_build_*` methods create the
   section containers, titles, and scrollable frames. Dynamic
   widgets are NOT created here.
3. **Dynamic rendering in `_refresh()`:** destroys old dynamic
   widgets (tracked in instance lists), re-queries, re-renders.
4. **Theme:** every widget construction calls `get_theme()` at
   render time, so theme-change refresh picks up new colors/fonts
   automatically. For ttk.Treeview widgets, re-apply the
   `ttk.Style().configure(...)` on every `_refresh` (D2).
5. **§17 compliance:** read from cache tables for fighter
   interpretation data; read from game-state tables for non-fighter
   data. NEVER touch `fighter_attributes` /
   `fighter_personality` / `fighter_contracts`.
6. **§14 compliance:** no raw attribute values displayed. Use
   `decode_phrase()` on cache-table voice-phrase columns. Use local
   voice bands for any raw 0-100 game-state values (transitional
   shim until the interpretation layer populates the corresponding
   `*_descriptors` table).
7. **Empty-state handling:** every section degrades gracefully (D5).
8. **Navigation:** use `state.set_active_screen(name)` for in-app
   navigation. For screens that need a parameter (like Fighter
   Profile needs a fighter_id), expose a `set_X(value)` method
   that the source screen calls BEFORE navigation (D4).
9. **Registration in `app.py`:** import the screen, create an
   instance with `self.screen_container` as parent, register with
   GameState, extend `_navigate` to handle the new screen name
   (pack_forget on navigate-away to preserve state, pack on
   navigate-to). Add the screen instance to the `preserved_screens`
   set so it isn't destroyed by the placeholder cleanup loop.
